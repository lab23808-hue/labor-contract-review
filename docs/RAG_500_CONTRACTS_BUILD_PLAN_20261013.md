# 500份合同评测集建设阶段——盘点、核验与方案（2026-10-13）

> 本报告对应用户指令的二、三、四、五部分（一的指标口径核验已单独交付于 `docs/RAG_METRIC_AUDIT_20261013.md`，不在此重复）。
> **本轮边界**：只做盘点/核验/调研/标准设计，未下载任何新合同、未修改生产 RAG 代码、未修改正式知识库。
> 下文每一条结论都标注了依据来源（设备上实际文件路径、脚本输出），不存在"看起来像真实合同所以算真实"的判断。

## 一、现有 50 份合同的真实来源分类（核心结论）

### 1.1 它们实际在哪里——两套容易混淆的目录，必须先分清

设备上有两处名字很像"合同"的目录，本轮逐一打开核实后确认是完全不同性质的数据：

| 目录 | 实际内容 | 本轮判断 |
|---|---|---|
| `data/contracts/`（22 个 UUID 命名的子目录） | `ContractManager` 应用运行时存储——每个目录是一次真实走完"上传合同→解析→审查→修改"全流程产生的运行态数据（`original_file/`、`parsed_text.txt`、`clauses.json`、`review/`、`versions/`、`modification_tasks/`）。多个目录的 `original_file` 文件名直接是"劳动合同.txt"或"劳动合同测试.txt"，`parsed_text.txt` 字节数高度重复（如 4401 字节出现 7 次）。 | **不是**用户指令里说的"50份合同"评测集，是开发/测试期间手动跑通流程留下的运行态痕迹，不计入本轮盘点对象。 |
| `data/eval_samples/contracts/`（50 个 .txt 文件） | 真正符合"50份合同评测集"描述的目录：`boundary_01~10.txt`、`clear_risk_01~20.txt`、`compliant_01~10.txt`、`mixed_01~10.txt`，恰好 10+20+10+10=50。每份都有对应的 `data/eval_samples/answers/*.json` 标准答案。 | **这是**本轮要审计的"50份合同"。 |

### 1.2 来源分类结论：全部 50 份均为**程序化模板拼装的合成测试数据**，不属于用户给出的四类（public-real / anonymized-real / human-written-test / source-unconfirmed）中的任何一类真实或半真实来源

依据（均为设备上实际文件，非推测）：

1. `data/eval_samples/manifest.json` 对全部 50 个样本的 `"source"` 字段逐一标注为 `"newly_designed"`，`"generator"` 字段明确为 `"evaluation/generate_contracts.py"`。
2. 打开 `evaluation/generate_contracts.py` 确认：合同原文**不是**由人工逐篇撰写，而是由脚本从 `evaluation/clause_bank.py` 的"参数化条款原型"（如 `probation_salary(percent)`、`noncompete(years, compliant)`）里按预先写好的"配方"（`_CLEAR_RISK_DOMINANT`/`_COMPLIANT_EXTRA`/`_MIXED_RISK_PAIRS`/`_BOUNDARY_SETS` 这几个列表）选取、传参、拼接生成。该文件头部注释原话："不手写50份完整合同——那样标准答案和合同原文的一致性完全依赖人工反复核对，容易出错。"
3. `evaluation/clause_bank.py` 头部注释进一步说明：条款原型里引用的法条编号"全部来自 `data/knowledge/劳动合同法.txt` 实际收录的条文"（即条号是真实法律条文编号），但**条款正文本身（当事人双方名称、具体情境描述、数字参数）是开发者编写的测试用例**，不是来自任何真实劳动合同样本、不是从公开渠道采集、也不是对真实合同做匿名化处理的结果。
4. `clause_bank.py` 里 `ANNOTATED_BY = "claude-eval-generator-2026-10-10"`，并自带注释："本次标注人：开发者/模型本身，不是独立法律复核人员"——这是数据自带的、非本轮新增的如实声明。

**因此准确的分类应为（第五类，用户给出的四分类里没有完全对应项，这里不强行套用"human-written-test"，因为严格说原文不是人工逐篇写的，而是代码拼装的）：**

> **"程序化模板拼装的合成测试数据（synthetic, template-assembled by script）"** —— 条款原型（有限的几十个"构件"）由开发者手写，完整合同由脚本按固定规则排列组合生成；不是任何真实合同、匿名化合同或人工逐篇撰写的测试合同。

**不得**称这 50 份为"真实合同"（无论公开来源还是匿名化），也**不得**称其标注为"人工法律核验"——两点均有数据自带的反面证据，上面已逐一列出。

### 1.3 完整性与可解析性

对全部 50 份 `.txt` 原文和对应 `.json` 标准答案做了真实解析（脚本见下，非凭空断言）：

- 50/50 个 `.txt` 文件可正常以 UTF-8 读取，50/50 个 `.json` 文件可被 `json.loads` 正常解析，无损坏、无截断。
- 用 SHA256 对 50 份合同原文逐一计算哈希并两两比较：**0 组完全相同的重复文件**（50 个哈希值互不相同）。
- "近似重复/模板家族"：由于生成器的设计本身就是"同一 `sample_type` 内，条款原型从同一个 `_baseline_fillers()` 列表里轮换取用"，50 份合同天然按 `sample_type` 分成 4 个模板家族，家族内合同共享部分条款文字但组合与参数不同，不构成逐字重复：

  | 模板家族（sample_type） | 合同数 | clause_count |
  |---|---|---|
  | clear_risk | 20 | 每份 5 条 |
  | basically_compliant | 10 | 每份 9 条 |
  | mixed | 10 | 每份 7 条 |
  | boundary_complex | 10 | 5~6 条（因场景而异） |

- 条款总数：50 份合同共 **315 条条款**（与 `experiment_kb/working/data/eval_samples/retrieval_eval_samples.json` 已记录的"总样本315"逐数一致，证明两者是同一批条款数据，只是后者是从这 315 条条款里为检索评测额外构造 query/label 的产物，不是独立的另一批合同）。

### 1.4 标签（legal_basis）与人工核验状态

- 315 条条款中，**188 条**带有非空的 `legal_basis`（引用了具体法条），**127 条**的 `legal_basis` 为空列表——这与此前所有报告反复强调的"127条没有标签≠无相关法律依据"完全对应：这 127 条多数是"基线合规条款"（`compliant_clause_count` 对应的正常条款，本身不需要援引具体风险法条）或信息不足待核实条款，不是"检索失败"或"无关"，本轮未改变这一判断，只是第一次用真实解析逐条验证了 188/127 这两个数字的真实构成。
- `verification_status` 字段在 315 条条款里只出现两种取值：**`candidate`（309条）** 和 **`pending_review`（6条）**，**没有任何一条取值为 `verified`**——这是数据本身的声明，不是本轮新加的限定。6 条 `pending_review` 的具体原因（已逐条读取 `pending_review_note` 字段，非推测）：
  - `boundary_03_c02`、`boundary_08_c03`、`mixed_01_c05`、`mixed_10_c02`：加班费法定加成标准出自《劳动法》第四十四条，但生产知识库当前未收录《劳动法》，只能引用《劳动合同法》第三十条的一般性要求代替，法律依据链条不完整。
  - `boundary_04_c02`、`boundary_09_c02`：试用期工资条款缺少具体数额，无法判断是否符合 80% 下限，需要补充信息后才能判断。

  这 6 条的 `verification_status=pending_review`、不是 `verified`，与知识库现有已知局限（《劳动法》未收录、文本未逐字核验，见 `data/knowledge/SOURCES.md`）直接对应，本轮确认这是真实的数据局限，不是遗漏。

### 1.5 查询(query)与相关法条标注的可用性（供检索评测用）

- 这 50 份合同的条款数据本身**不直接是**检索评测用的 query——检索评测用的 query/label 由另一个脚本 `scripts/build_retrieval_eval_samples.py`（此前轮次已确认）调用生产函数 `agents.review_agent.generate_query` 对这 315 条条款生成查询，再用条款自带的 `legal_basis` 作为相关法条标签，产出 `experiment_kb/working/data/eval_samples/retrieval_eval_samples.json`（315 条样本，188 条可评估，127 条因 `legal_basis` 为空被排除，与本节 1.4 的 188/127 精确对应）。
- 换言之：**这 50 份合同本身自带的"标准答案"是风险判断答案（`ContractAnswer`/`ClauseAnswer`，供合同审查功能评测用），不是检索评测的 query+相关法条——后者是衍生自前者的另一层产物**，本轮确认两者口径一致（188/127 对得上），但是两个不同的数据层，不能混为一谈。

## 二、目前可靠的已标注数据规模（汇总结论）

| 数据层 | 规模 | 可靠程度 |
|---|---|---|
| 合同原文+风险判断标准答案（`ContractAnswer`） | 50 份合同，315 条条款 | 条款原型由开发者编写并有明确的规则依据（如 `probation_salary_below_80_percent`），但 `verification_status` 全部是 `candidate`/`pending_review`，无一条 `verified`——**不是专业法律人员逐条人工复核的结果** |
| 检索评测用 query+相关法条标签（`retrieval_eval_samples.json`） | 315 条样本，188 条可评估（有 legal_basis），47 个去重后的独立查询场景 | 标签直接继承自上一层的 `legal_basis`，核验程度同上，**非独立法律复核** |
| 法律知识库本身（`data/knowledge/劳动合同法.txt`） | 26 条 Evidence（生产） | 条号真实存在、与 `SOURCES.md` 记录一致，但条文**文本本身**未逐字核验官方原文（`SOURCES.md` 明确声明的已知局限，本轮未解决也不在本轮范围内） |

**没有任何一层数据达到"专业法律人员人工核验"的标准**——这是本轮盘点最重要的结论，决定了下一步补充数据时不能想着"沿用现有标注方式批量扩充"，而要先解决"由谁、按什么流程做真正的人工法律核验"这个更基础的问题。

### 3.2 实际可达到的数量与差距的坦诚说明

- **本轮没有下载、采购、或获得任何一份新合同**（遵照用户边界要求）。
- 基于上述调研，**真实公开渠道能稳定提供"完整劳动合同全文+可靠标签"的数量，本轮无法给出确定数字**——因为：
  1. 裁判文书网等渠道提供的是"争议片段"而非完整合同全文，不能直接计数为"一份合同"。
  2. 政府示范范本数量有限（一般每个地区 1~3 个版本），且风险条款覆盖面天然不足。
  3. 是否存在可商用的现成中文劳动合同语料数据集，本轮未实际检索确认，不能假设存在。
- **唯一能确定、可控、免费地快速扩充数量的方式是扩展 `evaluation/clause_bank.py` + `generate_contracts.py` 生成更多合成合同**——但这只能扩大"合成测试集"规模，不能替代"真实评测集"，必须单独标注来源、单独统计，不能凑进"500份评测集"这个数字时掩盖其合成属性。
- **若目标是"500份里相当比例必须是真实合同"，现实的差距是：目前 0 份确认为真实来源（public-real/anonymized-real），450份的缺口在现有已调研渠道下大概率无法单靠公开渠道全部填满，需要用户决定是否提供内部真实合同（脱敏后使用），或接受"500份里除50份合成测试集外，剩余部分主要仍是合成数据，按场景设计扩充，明确标注为合成，不冒充真实"这一替代方案。**

### 4.3 默认分组与 80/20 切分、模板泄漏检查方法（设计说明，未实现代码）

1. **分组键**：先按 `template_family`（合成数据=`sample_type`，真实数据=按来源批次/相似度聚类后的家族ID）分组，再在家族内按"合同+模板家族"整体分配 split，不允许同一份合同的不同条款分散到 dev 和 test 两侧（即 `split_group_key` 必须是合同级或模板家族级，不能是条款级）——这是防止"模板泄漏"的核心规则：如果训练/调参阶段看过某个模板家族里的几份合同，测试阶段又用同家族的另几份合同，等于让模型在"记住模板套路"而不是"真正理解条款"的情况下刷出虚高分数。
2. **80/20 切分**：对分组后的家族列表做切分，而不是对条款列表直接切分——先统计每个 `template_family` 的合同数，按 80/20 比例在家族内部切分合同（不是条款），确保切完后 dev/test 两侧都覆盖到全部家族（避免某个家族整体被分到一侧导致另一侧缺失该类型样本）。
3. **泄漏检测**：切分后执行一次自动校验——对每个 `record_id`，确认其 `template_family` + `split_group_key` 对应的合同集合里，没有任何合同的条款同时出现在 dev 和 test 两侧；如果检测到，报错而不是静默修正。
4. **"pending"而非默认值**：任何 `verification_status` 不是 `candidate`/`pending_review`/`verified`中有把握的那个值、或 `relevant_law.pairs` 无法确定的样本，`dataset_split.split` 必须显式设为 `pending`，**不能默认赋值为 `dev` 或 `test`，更不能把"没有标签"直接等同于"relevant_law.pairs=[]"（即不能把"没标注"和"确实无关"混为一谈）**——这是对用户指令里"没有可靠标注的样本必须保持'pending'"这一要求的直接落实。
