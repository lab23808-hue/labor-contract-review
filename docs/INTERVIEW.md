## A. 项目总览与定位

**A1. 用一分钟介绍这个项目。**

- **为什么问**：看你能不能讲清楚"做什么、怎么做、做到哪一步"。
- **回答思路**：输入劳动合同文本 → 切成条款 → 逐条用 RAG 检索《劳动合同法》依据 + LLM 判断 → 规则分支补充确定性检查 → 两个分支并行、汇合成统一的审查结果。真实环境验证过：5 个条款 → 5 条 LLM 结果 + 2 条规则结果 → 7 条，0 失败。**主动说明边界**：只能解析 txt、知识库是 14 条节选、没有 API。
- **对应位置**：`README.md` 第 1、3、17、18 节。

**A2. 你的系统是 Agent 吗？**

- **为什么问**：很多人把"用了 LLM 和 LangGraph"直接叫 Agent，面试官会追问定义。
- **回答思路**：严格说**不是**。Agent 的关键是 LLM 动态决定下一步做什么、调用什么工具；我的流程拓扑是固定的，LLM 只在 `llm_review` 节点里做判断，检索是写死的步骤。更准确的说法是"LLM 增强的 workflow，用 LangGraph 编排"。承认这一点比硬说是 Agent 更可信。
- **对应位置**：`docs/KNOWLEDGE_TREE.md` 第二节"Agent 架构"。

**A3. LLM、RAG、规则、Workflow 在你项目里是什么关系？**

- **为什么问**：考察对各概念边界的理解。
- **回答思路**：Workflow 是骨架（LangGraph 图）。RAG 是 `llm_review` 内部的检索步骤，为 LLM 提供真实法条，避免凭记忆编造。LLM 做概率性的判断。规则是确定性代码，补 LLM 结构上做不到的（跨条款）和不保证可复现的部分。
- **对应位置**：`review/reviewer.py`、`rules/checker.py`、`review/pipeline.py`。

**A4. 为什么不直接把整份合同丢给 LLM？**

- **为什么问**：考察设计取舍，而不是"能用就行"。
- **回答思路**：实际做的取舍是逐条审查：① 结果要落到具体条款，便于定位；② 每个条款检索的法条不同；③ 某一条失败不会拖垮整份审查（`failed_clauses`）。**代价也要说**：逐条审查看不到其他条款，真实验证里 LLM 自己说"未提供合同期限，无法判断"——所以才需要规则分支。我没有验证过"整份丢给 LLM"的效果，不能声称它更差。
- **对应位置**：`docs/PITFALLS.md` P-04。

## B. LangGraph

**B1. 为什么用 LangGraph，而不是简单的函数串联？**

- **为什么问**：考察选型有没有依据、会不会夸大。
- **回答思路**：**诚实回答**：目前只有一个 fork/join，用函数加线程池也能实现。选它的理由是：拓扑用声明的方式写出来，结构可读、可测；并行与汇合的语义由框架保证；State 显式类型化，节点只通过 State 通信；将来要加条件边、重试、checkpoint 时不用重写。同时说明：这些进阶能力我**目前一个都没用到**。
- **对应位置**：`review/pipeline.py: build_graph`。

**B2. State 是什么？你存了什么、没存什么？**

- **为什么问**：State 设计是 LangGraph 项目的核心。
- **回答思路**：State 是节点之间共享的数据通道，6 个字段：`contract_id`、`clauses`、`llm_results`、`rule_results`、`final_results`、`failed_clauses`。判断标准是"这一步的产出，下一个节点是否把它当直接输入"。所以 `parsed_text`（切分后没人用）、`Evidence`（`ClauseReviewer` 内部局部变量）、基础设施实例都不进。`contract_id` 是引用，`clauses` 是数据本身。
- **对应位置**：`ReviewGraphState`；`README.md` 第 8 节。

**B3. 你有哪些 Node？各自调用什么？**

- **为什么问**：确认你清楚自己的系统。
- **回答思路**：5 个：`contract_loading`（`parse_contract` → `split_contract`）、`llm_review`（逐条 `ClauseReviewer.review`）、`rule_check`（`RuleChecker.check`）、`merge`（`merge_review_results`）、`report_assembly`（构造 `ReviewReport`）。节点只是薄封装，业务逻辑留在能独立测试的模块里。
- **对应位置**：`review/pipeline.py`。

**B4. 为什么 LLM 与规则检查可以并行？**

- **为什么问**：考察你是不是根据数据依赖做的设计。
- **回答思路**：因为函数签名上没有依赖：`RuleChecker.check(clauses)` 只吃 `clauses`，不读 `llm_results`；`ClauseReviewer.review(clause)` 也不读规则结果。而且规则的职责是独立补充，不是审核 LLM。
- **对应位置**：`rules/checker.py`。

**B5. 两个分支怎么汇合？**

- **为什么问**：追问机制，区分"图结构的汇合"与"业务合并"。
- **回答思路**：两层：图结构层，`llm_review → merge` 与 `rule_check → merge` 两条边，框架等两个上游都完成才执行 `merge`；业务层，`merge_review_results` 只是把两个列表拼接。
- **对应位置**：`pipeline.py` 的边定义；`rules/merge.py`。

**B6. 怎么保证并行结果不互相覆盖？**

- **为什么问**：并发写入是并行图最常见的坑。
- **回答思路**：每个 State 字段只有一个节点写入，所以不需要 reducer。如果两个并行节点写同一个 key，LangGraph 需要你声明怎么合并，否则会拒绝。业务上，`ReviewResult` 是风险点粒度，`merge` 不覆盖也不去重，LLM 结果与规则结果都保留。
- **对应位置**：`test_branches_join_at_merge_without_overwriting`、`test_rule_hit_clause_keeps_both_llm_and_rule_results`。

**B7. 异常怎么处理？为什么不做条件边和重试？**

- **为什么问**：考察你对"先做最小可用"的取舍是否有意识。
- **回答思路**：这是有意的架构决策：除了 LLM 单条款失败会被收进 `failed_clauses`，任何节点异常都直接终止整图。原因是锁定的 State 里没有能装"整节点失败"的字段，条件边没有路由信号；先跑通主链路，用真实使用决定是否值得增加失败处理。真实 LangGraph 1.2.12 上确认过：Contract Loading 抛的异常、与 LLM 分支并行的 Rule Check 抛的异常，都是原样向上抛出（测试确认到 `isinstance` 这一级，且只在这个版本上验证过）。
- **对应位置**：`docs/PITFALLS.md` P-14；`test_contract_loading_error_propagates...`、`test_rule_check_error_propagates`。

**B8. `Evidence` 为什么不进 State？**

- **为什么问**：追问 State 设计的判断依据。
- **回答思路**：三点：后续没有节点需要它；它只是 `ClauseReviewer.review()` 里的局部变量，函数返回的是 `ReviewResult`；`ReviewResult` 目前也没有字段能装它，放进 State 也进不了最终报告。如果以后要做审计展示，正确顺序是先给 `ReviewResult` 加字段，再谈 State。**要承认**：现在确实无法事后审计"模型看到了哪些法条"。
- **对应位置**：`review/reviewer.py: review`。

**B9. `ReviewReport` 为什么不进 State？带来什么后果？**

- **为什么问**：考察你是否清楚自己设计的副作用。
- **回答思路**：State 明确不加 `report` 字段，所以 `report_assembly` 构造后对象被丢弃；调用方用最终 State 里的 `contract_id` / `final_results` / `failed_clauses` 重建，构造是纯函数，可重复。这是已知取舍，不是遗漏。
- **对应位置**：`README.md` 第 7、18 节；`test_report_can_be_rebuilt_from_final_state`。

## C. RAG

**C1. 为什么按"条"切分法律文本？**

- **为什么问**：考察 chunk 策略是否有依据。
- **回答思路**：法律条文天然逐条罗列，一条一个 chunk，检索出来的是完整、有条号的条文，不会是半句话；只有超过 500 字才二次切分。
- **对应位置**：`rag/loader.py`。

**C2. 为什么用 BGE-M3？为什么只用稠密向量？归一化有什么用？**

- **为什么问**：考察对 embedding 选型的理解。
- **回答思路**：BGE-M3 多语言、对中文友好。当前只用稠密向量，够做基础语义检索；稀疏 / 多向量混合检索是后续可评估的方向。`normalize_embeddings=True` 是 BGE 系列推荐的用法，让内积等价于余弦相似度，分数更稳定。我没有做过不同 embedding 模型的对比实验，不要说"它是最优的"。
- **对应位置**：`rag/embedding.py`。

**C3. 检索分数怎么看？**

- **为什么问**：考察是否理解 distance。
- **回答思路**：`distance` 越小越相似，具体度量取决于 Chroma 配置，项目不做二次加工，所以数值没有绝对含义、不同集合之间不可比。真实结果里，相关条文的 distance 明显小于不相关的（例如 0.4469 对 0.6457、0.8028）。目前没有"相关性阈值"，这是后续可做的。
- **对应位置**：`README.md` 第 9 节；`docs/DEVLOG.md` R-01。

**C4. 你在检索上遇到过什么问题？**

- **为什么问**：考察真实排查能力。
- **回答思路**：竞业限制条款的检索找不到第二十三、二十四条。定位过程是：对比"短 query 单独检索"与"审查时实际 query 的检索"，发现只有 query 不同；原因是 `generate_query` 把"第X条 标题"整行删掉，标题里的"竞业限制"丢了，而正文是同义改写。修复后第二十四条排第一。关键点：单元测试全绿，真实检索才暴露。
- **对应位置**：`docs/PITFALLS.md` P-03。

**C5. 知识库覆盖不到的条款怎么办？**

- **为什么问**：考察对 RAG 边界的认识。
- **回答思路**：Prompt 要求依据不足要如实说明，所以正常工时条款得到的是"依据不足，未发现冲突"，而不是编造。要区分 `risk=False` 的两种含义："确认合规"与"依据不足所以没发现冲突"。补内容属于扩充知识库的工作。
- **对应位置**：`docs/PITFALLS.md` P-13。

## D. LLM Review

**D1. 怎么保证 LLM 输出是合法 JSON？**

- **为什么问**：LLM 输出的可靠性是工程重点。
- **回答思路**：多层：Prompt 明确要求只输出 JSON 及五个字段；调用时启用 JSON 模式；拿到后先 `json.loads`，再校验成 `LLMReviewOutput`（`risk` 必须与 `risk_level` 一致）；任何一步不合法都抛 `ReviewError`，带 `clause_id` 与原始输出，不做静默兜底。目前**没有重试**。
- **对应位置**：`review/reviewer.py: _parse_llm_output`、`review/schemas.py`。

**D2. 为什么 `LLMReviewOutput` 和 `ReviewResult` 分开？**

- **为什么问**：考察数据建模。
- **回答思路**：一个描述"要求模型返回什么"，一个是系统内部的规范结果。`clause_id`、`source` 是代码知道的事实，不该让模型填，也不该让模型有机会填错。分开之后，模型输出的校验与最终结果的一致性校验各管各的。
- **对应位置**：`docs/DEVLOG.md` 3.7。

**D3. 怎么防止模型编造法条？**

- **为什么问**：LLM 幻觉是必问题。
- **回答思路**：**如实回答**：目前靠 Prompt 约束（只能引用给定的法律依据、依据不足要说明）和真实验证中的人工观察（三个案例里 `legal_basis` 都来自给定的检索结果），**没有程序去校验 `legal_basis` 是不是真的出自 `Evidence`**。这是一个可以补的点。
- **对应位置**：`llm/prompts.py: SYSTEM_PROMPT`。

**D4. LLM 结果不稳定怎么办？**

- **为什么问**：考察对非确定性的认识。
- **回答思路**：`temperature=0` 也不保证可复现。真实数据：同一份 10 条款合同两次运行，`clause_001`、`clause_009` 从 `low` 变成 `none`，而证据明确的高风险条款两次都稳定。我的处理是接受并记录，规则是唯一可复现的部分；候选方案（自洽性采样、只对 `none` / `low` 重复采样）成本会上升，没有做。
- **对应位置**：`docs/PITFALLS.md` P-05。

## E. 规则检查

**E1. 为什么需要规则？不能全交给 LLM 吗？**

- **为什么问**：追问规则分支的价值。
- **回答思路**：真实数据给出了两个理由：LLM 单条款审查看不到其他条款（试用期条款的 LLM 原话"条款未载明合同期限，无法判断"，规则用 `clause_001 + clause_003` 给出确定性结论）；LLM 结果不保证可复现。规则不是"给 LLM 兜底"这么笼统，而是补主线路**结构上**做不到的部分。
- **对应位置**：`docs/DEVLOG.md` R-04。

**E2. `RuleChecker` 为什么不依赖 `llm_results`？**

- **为什么问**：考察对模块独立性的理解。
- **回答思路**：规则要能独立运行、独立测试；如果只在 LLM"不确定"时才运行，规则的价值就受制于 LLM 的自我评估。它根据条款原文和自己的适用条件判断。
- **对应位置**：`RuleChecker.check(clauses)` 的签名。

**E3. 为什么不做通用规则引擎 / 统一事实抽取层？**

- **为什么问**：考察是否识别过度设计。
- **回答思路**：第一版我确实建了 `ContractFacts` 统一事实层，后来意识到规则是**测试驱动的补丁**：哪类问题被漏检，才补哪条规则，提前建通用层是过度设计，于是删除，改成每条规则自己识别、提取、判断。代价是各规则可能有重复的提取逻辑；我定了触发线：出现第二条需要同一段提取的规则时，再抽成共享的小函数，仍不恢复统一层。
- **对应位置**：`docs/PITFALLS.md` P-06。

**E4. `merge` 为什么不覆盖、不去重？**

- **为什么问**：考察对数据粒度的理解。
- **回答思路**：`ReviewResult` 是风险点粒度，一个条款可有多条结果。规则命中就整条替换 LLM 结果，会丢掉 LLM 发现、规则没检查的其他风险；纯拼接是唯一不丢信息的做法。代价是同一个风险可能出现两条内容相近的结果，v1 接受，等真实数据证明重复率过高再做去重。
- **对应位置**：`rules/merge.py`；`docs/PITFALLS.md` P-07。

**E5. 怎么新增一条规则？**

- **为什么问**：考察可扩展性。
- **回答思路**：真实测试确认稳定漏检 → 新建文件，函数签名 `list[Clause] -> list[ReviewResult]`，只在发现问题时返回、填 `rule_id`、`source=rule` → 在 `RuleChecker.__init__` 注册 → 补单元测试（含"没问题返回空"和"提取不到就跳过"）→ 跑真实脚本验证。
- **对应位置**：`README.md` 第 10 节。

## F. 测试

**F1. 为什么分 Unit / Module / Graph / E2E 四层？**

- **为什么问**：考察测试设计思路。
- **回答思路**：分层是为了失败时能定位到层，也便于只跑最快的那层。Unit 验证局部逻辑，Module 验证真实组件协作，Graph 验证拓扑与状态流转，E2E 验证真实系统链路。各层解决的问题不同，缺一不可（见 F2、F3、F4）。
- **对应位置**：`tests/README.md`、`tests/conftest.py`。

**F2. Mock 和真实 E2E 有什么区别？为什么不能全部用 Mock？**

- **为什么问**：经典问题，看你有没有真实经历。
- **回答思路**：Mock 只验证"我以为它怎么工作"。三件事只有真实调用才暴露：DeepSeek 旧模型名已下线；`generate_query` 丢标题关键词导致召回失败；`HuggingFaceEmbeddings` 构造即加载模型。反过来，Mock 让单元测试快、稳定、不花钱、能制造失败路径。所以两者互补，不是二选一。
- **对应位置**：`docs/PITFALLS.md` P-01、P-02、P-03。

**F3. 为什么真实 E2E 不能替代单元测试？**

- **为什么问**：追问另一面。
- **回答思路**：E2E 慢、花钱、依赖网络；LLM 有非确定性（`clause_001` 就翻转过），失败时定位不到层；无法按需制造"LLM 单条失败""规则抛异常""第十九条每一档边界值"这类场景。
- **对应位置**：`docs/KNOWLEDGE_TREE.md` 第三节。

**F4. 你怎么测试 LangGraph？为什么不能只测最终结果？**

- **为什么问**：LangGraph 项目的测试难点。
- **回答思路**：用真实 `langgraph`，只把 LLM 和检索换成假对象，其他全部真实。断言的是结果而不是引擎内部顺序：两个分支都被调用、`final_results = llm_results + rule_results`、LLM 全失败时规则分支照常出结果、`failed_clauses` 只含失败条款、异常向上抛出。不能只测最终结果：数量对不代表路径对，失败路径和异常传播只看成功那次采样是看不到的。**注意口径**：这 12 个测试在真实 LangGraph 1.2.12 上通过；替身只在沙箱里做过逻辑自检。
- **对应位置**：`tests/test_review_pipeline.py`。

**F5. 你怎么证明测试不是假绿？**

- **为什么问**：考察测试质量意识。
- **回答思路**：做变异检查：故意把 merge 改成覆盖式、把规则异常吞掉、让 LLM 永不失败，对应测试都变红，还原后全绿。另外断言写"具体结果"（`llm.calls == 3`），不写"没报错"。**局限要说**：手工做的、只覆盖几个点、是在沙箱替身上做的，不是自动化的变异测试。
- **对应位置**：`docs/PITFALLS.md` P-12。

**F6. marker 的"使用"和"注册"有什么区别？`conftest.py` 与 `pytest.ini` 各管什么？**

- **为什么问**：真实踩过的坑。
- **回答思路**：使用只是创建标签，任意名字都能创建（故意宽松，所以拼错名字不会崩）；注册是在配置里声明"这些名字是有意使用的"，警告是为了防拼写错误，不应该靠关闭警告解决。`conftest.py` 放钩子和共享逻辑（这里按文件名自动分层），`pytest.ini` 放静态配置（路径、marker 注册）。真实情况：3 条警告的根因是本地 `pytest.ini` 没同步，不是代码问题。
- **对应位置**：`docs/PITFALLS.md` P-11。

## G. 工程

**G1. 为什么做配置集中？有什么副作用？**

- **为什么问**：考察对重构代价的认识。
- **回答思路**：8 处散落的默认值和路径集中到 `config/settings.py`，改一处生效，且不放密钥。副作用：依赖图变了（原来只依赖 `schemas` 的模块现在还依赖 `config`），所以要让 `config` 零依赖并用测试守住；默认参数在函数定义时求值，改配置需重启；`config` 是通用包名，要确认没有被第三方同名包抢占。
- **对应位置**：`docs/PITFALLS.md` P-09；`tests/test_config_settings.py`。

**G2. 两个 chunk 配置为什么不合并成一个？**

- **为什么问**：考察"重复"与"耦合"的区分。
- **回答思路**：合同条款切分和法律知识切分是两个互相独立的模块，都是 500/50 只是巧合。共用一个常量，调其中一个会悄悄影响另一个。所以分成 `CLAUSE_CHUNK_*` 与 `KNOWLEDGE_CHUNK_*`。
- **对应位置**：`config/settings.py`。

**G3. 合同存储为什么用文件系统？怎么防路径穿越？**

- **为什么问**：考察存储选型与安全意识。
- **回答思路**：当前只需要按合同隔离的中间产物，没有检索、并发需求，用文件系统足够；`contract_id` 用 uuid4 十六进制，并且在访问任何目录前用正则校验，防止 `../` 穿出根目录（因为它以后会来自 API）；原文件只写一次、不允许覆盖；`metadata.json` 最后原子写入，创建失败会整体清理。**要说明**：早期设想过 SQLite，没有实现，代码里个别文档字符串还留着这个说法。
- **对应位置**：`contract/manager.py`。

**G4. 你怎么证明整理没有改变行为？**

- **为什么问**：考察重构的验证方法。
- **回答思路**：三层证据：11 项默认值前后逐项等价（独立重算整理前的写法来对比）；生产代码改动面只在 9 个文件，未触碰 `pipeline`、规则、Prompt、`schemas`、`parser`；真实环境 258 测试通过、graph 12 通过，真实 E2E 复跑无问题。
- **对应位置**：`docs/DEVLOG.md` 3.10、R-05 至 R-07。

## 不要说的话

下面这些说法与真实情况不符，或者超出了验证过的范围：

- ❌"这是一个自主 Agent"→ 它是 LLM 增强的 workflow。
- ❌"LLM 的审查结果是稳定 / 可复现的"→ 有真实翻转案例。
- ❌"系统能审查任何合同 / 覆盖整部劳动法"→ 知识库只有 14 条节选，规则只有 2 条。
- ❌"支持 PDF / Word"→ 只支持 `.txt`。
- ❌"有 API / 前端"→ `api/`、`output/` 是空包。
- ❌"已经防止了模型编造法条"→ 只有 Prompt 约束和人工观察。
- ❌"用了条件边 / checkpoint / 重试"→ 一个都没用。
- ❌"合同元数据存在 SQLite / 数据库里"→ 是文件系统 JSON。
- ❌"在所有 LangGraph 版本下异常行为都是这样"→ 只在 1.2.12 上验证过。
- ❌"E2E 每次结果都完全一样"→ 规则部分稳定，LLM 部分的边界条款会变。
- ❌"测试全部用真实服务跑的"→ 258 个自动化测试不联网；真实服务只用于 scripts 里的 E2E 与局部验证。
