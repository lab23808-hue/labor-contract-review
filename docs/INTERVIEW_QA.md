## 一、项目级

**Q1-1【面试问题】用一分钟介绍这个项目。**
- 【考察点】能不能讲清楚"做什么、怎么做、做到哪一步"，是否会夸大。
- 【我应该能够回答什么】完整数据流（上传→解析→切分→审查→律师提出修改→Agent 生成候选→人工确认→V2→Diff）+ 主动说明边界（只支持 .txt、知识库仅 14 条、无鉴权）。
- 【当前项目中的真实答案】输入劳动合同 `.txt` → 切成条款 → 逐条 RAG 检索《劳动合同法》依据 + LLM 判断 → 规则分支补充确定性检查 → 汇合成审查结果 → 律师对某条款发起修改任务 → Modification Agent（真实 Function Calling）生成候选 → Validator 校验 → 律师确认/拒绝（HITL）→ 生成 V2（完整重新解析/切分/审查）→ Clause Diff/Risk Diff 对比。真实环境验证过：5 条款→5+2→7（Review）；V1/V2 全链路经过三轮真实浏览器验收并修复了 3 个真实 bug（P-22/23/24）。
- 【容易答错的地方】把"已经完整实现 API+前端+Modification Agent"说成"还是脚本原型"——这是过时信息；也不要反过来把项目能力夸大成"支持任意格式合同"。

**Q1-2【面试问题】你的系统是 Agent 吗？**
- 【考察点】是否清楚 Agent 和"用了 LLM"的区别。
- 【我应该能够回答什么】区分 Review 链路（不是 Agent）和 Modification 链路（是一种受限的 Agent）。
- 【当前项目中的真实答案】Review 链路的 LLM 调用不是 Agent——流程固定，LLM 只在一个节点里判断。Modification Agent **是** Agent，但是"带校验和人工确认的单次工具调用 Agent"：由 LLM 通过真实 Function Calling 决定是否调用唯一的工具 `modify_clause`，但不做多工具选择、不做多步规划、不能自主生效（必须人工确认）。
- 【容易答错的地方】笼统地说"整个系统是 Agent"或"整个系统都不是 Agent"，都不准确——要分链路说清楚。

**Q1-3【面试问题】项目当前做到什么程度，边界在哪里？**
- 【考察点】是否诚实、是否清楚已实现和未实现的边界。
- 【我应该能够回答什么】列出已实现（见项目知识库第一节）和未实现（PDF/DOCX、鉴权、批量、SQLite）。
- 【当前项目中的真实答案】api/ 和 output/ 中，api/ 已完整实现（含 Modification 全链路），output/ 仍是空包；只能解析 `.txt`；知识库仅 14 条节选、规则仅 2 条；没有用户权限体系。
- 【容易答错的地方】旧文档（README.md、docs/INTERVIEW.md 原始内容）里"api/output 都是空包"的说法已经不准确，回答时要用当前真实状态。

## 二、架构级

**Q2-1【面试问题】LLM、RAG、规则、Workflow、Agent 在你项目里分别是什么关系？**
- 【考察点】概念边界是否清晰。
- 【我应该能够回答什么】用一句话定位每个概念在本项目里的角色。
- 【当前项目中的真实答案】Workflow 是骨架（Review 用 LangGraph，Modification 用手写状态机）；RAG 是证据层，不决定审查范围；LLM 做概率性判断（Review）和生成（Modification）；规则是确定性补丁；Agent 特指 Modification Agent（真实 Function Calling+自主决策）。
- 【容易答错的地方】把 RAG 说成"决定要不要审查这个条款"——RAG 只提供证据，审查范围由 ClauseSplitter 的切分结果决定。

**Q2-2【面试问题】为什么不直接把整份合同丢给 LLM？**
- 【考察点】设计取舍是否有依据，是否承认代价。
- 【我应该能够回答什么】逐条审查的三个理由 + 一个已知代价（看不到其他条款）+ 规则如何补这个代价。
- 【当前项目中的真实答案】结果要落到具体条款便于定位；每个条款检索的法条不同；单条失败不拖垮整体。代价：真实验证里 LLM 自己说"未提供合同期限，无法判断"（P-04），靠规则分支补上。
- 【容易答错的地方】声称"整份丢给 LLM 效果更差"——没有做过对比实验，不能这样说。

**Q2-3【面试问题】API 层是怎么组织的？为什么不在 app.py 里直接写业务逻辑？**
- 【考察点】分层设计的理解。
- 【我应该能够回答什么】`app.py` 只做三件事（创建实例/挂 lifespan/留路由挂载点）；`dependencies.py` 只做接线（lifespan+AppState+Depends）；`routes/*.py` 只做 HTTP↔业务模块的翻译，不重复实现任何业务逻辑。
- 【当前项目中的真实答案】见 `api/app.py`/`api/dependencies.py` 顶部注释——业务逻辑全部在 `contract`/`parser`/`clause`/`review`/`rules`/`modification` 里，路由只负责调用+异常映射。
- 【容易答错的地方】把 `ModificationTaskCreate` 这类 HTTP 层 DTO 和 `schemas.ModificationTask` 这类业务对象混为一谈——它们是两个不同层次的东西。

## 三、Agent

**Q3-1【面试问题】Modification Agent 和普通的"让 LLM 输出 JSON 再解析"有什么本质区别？**
- 【考察点】是否理解真正的 Function Calling。
- 【我应该能够回答什么】区分"请求里声明 tools，模型自己决定调不调用、怎么填参数"和"Prompt 里要求输出 JSON，代码里 json.loads 解析"。
- 【当前项目中的真实答案】`modification/agent.py` 调用 `llm/client.py::chat_with_tool`，请求带 `tools=[MODIFY_CLAUSE_TOOL_SCHEMA]`、`tool_choice="auto"`，DeepSeek 返回真实的结构化 `tool_calls`；决策权（要不要调用）确实在模型手里，不是代码里的 if/else。第一版只有一个工具，看起来"总会调用"，但机制上是真 Function Calling。
- 【容易答错的地方】说"反正只有一个工具，和普通 JSON 输出没区别"——机制不同：真实数据显示模型确实有一定概率（社区报告约 25%）选择不调用工具直接回文本，这条路径已经被 `if not tool_calls: raise` 覆盖。

**Q3-2【面试问题】为什么 Validator 不用 LLM 自己检查自己？**
- 【考察点】对 Agent 输出可信度工程化处理的理解。
- 【我应该能够回答什么】固定规则能可靠检测的问题（越界、占位符、编号丢失），不需要再调用一次 LLM。
- 【当前项目中的真实答案】`modification/validator.py::validate` 是纯函数，用正则检测越界条款编号、占位符模式、结构完整性，不调用 LLM——这是硬约束（模块顶部注释明确写出）。
- 【容易答错的地方】认为"用 LLM 再检查一遍会更准确"——LLM 自我审查本身不可靠，且引入了新的不确定性和成本。

**Q3-3【面试问题】Reject 之后为什么不基于上一轮候选继续改？**
- 【考察点】是否理解这个设计对防止"越改越差"的作用。
- 【我应该能够回答什么】永远基于 V1 原文+全部历史意见重新生成，从代码结构上排除"在错误结果上叠加"。
- 【当前项目中的真实答案】`build_modification_messages` 函数签名本身不接受"上一轮候选文本"参数（`modification/prompts.py`），`start_modification` 每次都用 `task.original_text` 调用 Agent。
- 【容易答错的地方】以为这样做"效率低"——目前没有证据表明增量修改效果更好，且增量修改的工程复杂度更高（需要保证每轮输入干净）。

**Q3-4【面试问题】当前为什么没有多工具选择的 Agent？未来怎么加？**
- 【考察点】是否能识别"过度设计"，以及扩展思路是否清晰。
- 【我应该能够回答什么】当前业务需求只有一种操作（修改条款），过早设计多工具框架是没有真实需求支撑的过度设计；未来在 `modification/agent.py` 与 `service.py` 之间加路由层。
- 【当前项目中的真实答案】见 `docs/ARCHITECTURE_DECISIONS.md` AD-06/AD-07。
- 【容易答错的地方】说"技术上做不到"——技术上完全可以做，是业务需求和过度设计风险的权衡，不是能力问题。

- 【容易答错的地方】断言"这就是最优设计"——没有找到显式的设计讨论证据证明这是经过对比后的决策，只能说这是当前代码的真实状态和一个合理的解释。

**Q4-11（新增）【面试问题】如果要给 LangGraph 加条件边，你会怎么加？**

- 【我应该能够回答什么】需要先扩大 State（加一个能表达"节点失败/需要走哪条路"的字段），再用 `add_conditional_edges` 声明路由函数。
- 【当前项目中的真实答案】**本项目未实现**，这是诚实的边界——只能讲清楚"如果要做，需要先解决什么前置问题"，不能说"已经做过"。
- 【容易答错的地方】把"没做过"说成"做过但效果不好"——这两者是完全不同的诚实程度。

## 六、Review / 规则

（原 D1~D4、E1~E5 保留，合并到本节）

**Q6-1（原 D1）怎么保证 LLM 输出是合法 JSON？** Prompt+JSON 模式+`LLMReviewOutput` 校验，不合法就抛 `ReviewError`，无重试。

## 八、Bug-Debug

**Q8-1【面试问题】为什么 V2 中未修改条款出现额外空行？（必考题，需完整 现象→定位→根因→修复→验证 流程）**
- 【考察点】完整的真实排查能力，能否讲清楚每一步的推理链条，而不是背答案。
- 【我应该能够回答什么】完整的 STAR：
  - **现象**：条款级 Diff 里，没有被律师修改过的条款（clause_002~005、007、008），V2 文本相比 V1 在"标题"和"正文"之间多了一个空行，正文一字未变；被修改过的条款（clause_000、001、006）反而没有这个问题。
  - **定位**：最初怀疑是 `clause_diff` 缺少格式规范化。真实浏览器数据显示规律是"只和是否被修改相关，和条款结构无关"，排除了 `_build_v2_text`/`_reconstruct_article_text` 本身的问题（P-22 已验证过对未修改片段是逐字节保真的），把范围收窄到"重建出的文本之后又经过了什么处理"——只剩"写入临时文件"这一步。
  - **根因**：部署环境是 Windows（`os.linesep=="\r\n"`），V1 原始 `.txt` 文件本身是 CRLF 换行；未被修改的条款从 V1 原文原样切出，天然带 `\r\n`；`write_text(..., encoding="utf-8")` 默认 `newline=None`，会把字符串里裸的 `"\n"` 替换成 `os.linesep`，但不特殊处理已存在的 `"\r"`——于是 `"\r"+"\n"` 变成 `"\r"+"\r\n"`="\r\r\n"，多出一个 `\r`，被浏览器当成额外一次换行。被修改的条款文本来自 Agent 生成的干净 `"\n"`，不含预先存在的 `\r`，所以不触发这个问题。
  - **修复**：`generate_v2` 里改成 `tmp_path.write_text(v2_text, encoding="utf-8", newline="")`，完全关闭换行转换。
  - **验证**：`scripts/verify_p24_newline_write.py`（6/6，本沙箱是 Linux 无法复现具体故障，只能验证 `newline=""` 语义本身）；既有回归测试全部通过；**bh 在真实 Windows 环境重新生成 V2、真实浏览器核对确认**：未修改条款正确显示"未修改"，修改过的条款仍正确显示"已修改"。
- 【当前项目中的真实答案】见 `docs/PITFALLS.md` P-24（12 字段完整格式）。
- 【容易答错的地方】跳过"最初怀疑被推翻"这一步，直接说"一开始就知道是换行符问题"——真实过程是先怀疑 Diff 逻辑，再用数据排除，才收窄到 I/O 层，这个排查过程本身才是面试想考察的能力。

**Q8-2【面试问题】P-22（V2 重建丢款）是怎么发现和定位的？**
- 【考察点】能否讲清楚"用真实执行验证推翻最初假设"这个方法论。
