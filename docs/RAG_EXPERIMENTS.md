## 结论速览

当前保留的检索策略：**BM25（`char_bigram` 分词器，k1=1.5, b=0.75），生产 top_k=5**。

依次被验证并放弃的方向：扩大 Dense Top-K（收益有限）→ Dense+BM25 对称 RRF 融合（排序质量不如纯 BM25）→
jieba 分词器（MRR/nDCG 更差）→ 标点空白清理（改善是单场景噪声级别）→ 跨空白边界处理
（指标完全无变化）→ 加权 RRF（BM25偏重 1:2 排序质量优于对称基线，但仍不如纯 BM25，且会让部分
原本在 Top-5 的依据掉出 Top-5；是否采用待用户确认，详见第二节 09 号实验）。详见下面各节。

## 一、固定不变的评估基础

所有 01-08 号实验共用：

- **样本快照**：`data/eval_samples/retrieval_eval_samples.json`，由 `build_retrieval_eval_samples.py`
  从 50 份评估合同的标准答案（`agents.review_agent.generate_query` 真实生产函数生成 query，未修改）构建。
  共 315 条 `ClauseAnswer`，其中 188 条有可靠 `legal_basis` 标签（`evaluable=true`），127 条没有
  （`evaluable=false`，原因统一是"标准答案没有标注 legal_basis（通常是合规条款，没有对应的风险法条）"）。
- **双重统计口径**：
  - **原始样本口径**（188 条）：macro 平均，同一条款模板在不同合同里重复出现会被重复计数。
  - **独立场景口径**（47 个 `(query, 标签)` 场景）：每个去重后的场景等权重，不管现实中出现几次。
  两种口径永远分开报告，不合并。
- **评分公式**（`eval_retrieval_strategy_experiment.py` 的 `_score`/`_dcg`/`_aggregate`，后续全部复用，没有重新实现）：
  按 `(source, article)` 元组匹配；`recall = 命中的标准法条数 / 标准法条总数`；
  `mrr_contribution = 1/首次命中排名`（未命中为0）；`nDCG` 二值相关性，`DCG=Σ rel_i/log2(i+2)`（0-indexed），
  `IDCG` 用 `min(标准法条数, K)` 个理想命中计算；全部 macro 平均。
- **候选深度 / 截断深度**：`candidate_k=20`（每个通道内部检索的候选深度）与 `final_top_k∈{5,10,20}`
  （真正用于算指标的截断深度）严格区分，脚本和报告里永远分别标注，不混用。

## 二、各实验脚本说明（3.1）

### 01 `build_retrieval_eval_samples.py`

- **解决什么问题**：标准答案是 50 份合同 × 若干条款的 `ClauseAnswer` JSON，本身不是检索评估格式，需要转成
  `(query, 标准相关法条)` 的固定样本集。
- **为什么做**：后续所有检索实验需要一份不会变的输入，避免每次实验用不同的样本集，导致结果不可比。
- **输入**：`data/eval_samples/answers/*.json`、`data/eval_samples/contracts/*.txt`。
- **输出**：`data/eval_samples/retrieval_eval_samples.json`（315 条，含 `evaluable`/`exclude_reason` 字段）。
- **关键参数**：无检索相关参数，纯数据转换。
- **一致/变化的变量**：N/A（构建阶段，不是对照实验）。
- **运行目录**：项目根目录，`python scripts/build_retrieval_eval_samples.py`。
- **真实/静态/机制自检**：真实数据转换（调用真实 `generate_query`，未修改生产代码）。
- **结论依据**：N/A（不是对照实验，没有"结论"）。

### 02 `eval_retrieval_baseline.py`

- **解决什么问题**：在还没做任何策略对比之前，先measure 当前 Dense（BGE-M3）+ Chroma 在 top_k=5（生产默认配置）
  下的真实检索效果，建立基线。
- **为什么做**：任何后续"是否要改进/切换策略"的讨论都需要一个真实数字做参照，不能凭感觉。
- **输入**：`retrieval_eval_samples.json`（188 条 evaluable）+ 临时 Chroma collection（真实 BGE-M3 embedding，
  不碰官方 `data/chroma`）。
- **输出**：`data/eval_samples/results/retrieval_baseline_<时间戳>.json`。
- **关键参数**：`top_k=5`。
- **一致/变化的变量**：N/A（单组，没有对照）。
- **运行目录**：项目根目录（需要真实 BGE-M3 模型权重和网络，首次运行会下载模型）。
- **真实/静态/机制自检**：真实模型调用。两次真实运行（`221552`、`222707`）结果完全一致。
- **结论依据**：真实数据支持。Recall@5=0.9628（188条口径），命中177/188完全命中、8条部分命中、3条完全未命中。

### 03 `eval_retrieval_topk_experiment.py`

- **解决什么问题**：Dense 在 top_k=5 时有 3 条完全未命中、8 条部分命中，扩大 top_k 能不能把它们找回来。
- **为什么做**：在决定要不要上更复杂的策略（BM25/RRF）之前，先排除"只是 top_k 设置太小"这个最简单的可能性。
- **输入**：同 02，额外跑 `top_k=10、20`。
- **输出**：`data/eval_samples/results/retrieval_topk_experiment_<时间戳>.json`。
- **关键参数**：`final_top_k ∈ {5,10,20}`。
- **一致/变化的变量**：固定 Dense 模型和样本，唯一变化的是 top_k。
- **运行目录**：项目根目录（需要真实 BGE-M3）。
- **真实/静态/机制自检**：真实模型调用。
- **结论依据**：真实数据支持。见下方表 A。**决策：不继续单纯扩大 Dense Top-K**（Recall@20 比 Recall@5
  只提升约 1.6 个百分点，MRR/nDCG 几乎不变——说明问题不在召回深度，在排序本身），转而测试其他检索策略。

### 04 `eval_retrieval_strategy_experiment.py`

- **解决什么问题**：对比 Dense、BM25（自实现 BM25Okapi）、对称 RRF 融合三种策略，看哪个排序质量更好。
- **为什么做**：Dense 的 MRR/nDCG 明显偏低（排序质量差），需要验证纯关键词检索（BM25）或融合（RRF）
  是否能解决这个问题，而不是继续在 Dense 上调参。
- **输入**：`retrieval_eval_samples.json`（188条/47场景）+ 固定知识快照（26 个法条片段，`data/knowledge/*.txt`
  重新切分，并与官方 `data/chroma` 做内容一致性核验）。
- **输出**：`data/eval_samples/results/retrieval_strategy_experiment_<时间戳>.json/.md`。
- **关键参数**：`candidate_k=20`；BM25 `k1=1.5, b=0.75`；RRF `rrf_k=60`（未做参数搜索）；
  `final_top_k∈{5,10,20}`。
- **一致/变化的变量**：三种策略共用同一份知识快照（通过知识内容指纹 `_knowledge_content_fingerprint`
  强制校验，而不是只看样本数/模型名是否一致）、同一批样本/场景、同一套评分公式；唯一变化的是检索策略本身。
- **运行目录**：项目根目录；`--force-rerun-dense` 可强制重跑 Dense（而不是复用旧结果）。
- **真实/静态/机制自检**：真实运行。本次 Dense 是**真实重跑**（不是复用旧 topk 实验结果），
  因为旧结果文件没有保存知识内容指纹，无法证明旧 Dense 索引的知识内容和本次 BM25 完全一致
  （这条是用户明确要求补上的核验，见下方工程问题记录）。
- **结论依据**：真实数据支持。见下方表 B。**决策：BM25 排序质量在当前数据上最好；对称 RRF 虽然
  提高了部分召回率，但没有改善排序质量，暂不作为最终方案。**

### 05 `eval_bm25_tokenizer_experiment.py`

- **解决什么问题**：BM25 用的 `char_bigram` 分词器（过滤空白后两两配对）是否是合适的选择，`jieba`
  这种"更懂中文"的分词器会不会更好。
- **为什么做**：BM25 效果依赖分词质量，`char_bigram` 看起来比较粗糙（会产生跨边界伪 token），值得验证
  真正的中文分词是否带来提升——而不是预设 jieba 更好。
- **输入**：复用 04 的样本加载、知识库切分、BM25 索引、评分公式；新增 `_try_build_jieba_tokenizer()`
  （真实 `import jieba`，不可用就不编造结果）。
- **输出**：`data/eval_samples/results/bm25_tokenizer_experiment_<时间戳>.json/.md`。
- **关键参数**：`BM25_K1=1.5, BM25_B=0.75`（两组共用，不调）；`candidate_k=20`；`final_top_k∈{5,10,20}`。
- **一致/变化的变量**：唯一变量是分词器（`char_bigram` vs `jieba 0.42.1`）。
- **运行目录**：项目根目录；需要 `pip install jieba==0.42.1` 才能跑 jieba 分支，否则只报告 char_bigram
  结果并明确说明 jieba 未安装，不编造 jieba 数字。
- **真实/静态/机制自检**：真实运行（jieba 0.42.1 真实安装后真实调用）。
- **结论依据**：真实数据支持。见下方表 C。**决策：保留 `char_bigram`**。Recall@20 两者相同，但
  jieba 的 MRR/nDCG 明显更差——原因是 jieba 把"第二十六条"这类条文编号切成一个原子 token，
  几乎不会和真实的条款描述型 query 匹配上；而"社会保险"这类常见法律短语又被切成一个整体，
  丢失了字级别的部分匹配能力。

### 06 `eval_bm25_preprocessing_experiment.py`

- **解决什么问题**：`char_bigram` 不清理标点和多余空白，直接对原文配对。清理一下（统一换行、折叠连续
  空白、剔除所有 Unicode 标点）会不会提升效果。
- **为什么做**：标点和空白理论上是噪声，清理后分词应该更"干净"，值得验证是否真的转化成检索质量提升。
- **输入**：复用 04/05 的样本、知识库、BM25 索引、`_run_one_tokenizer()` 通用跑分函数。
- **输出**：`data/eval_samples/results/bm25_preprocessing_experiment_<时间戳>.json/.md`。
- **关键参数**：同上，唯一变量是是否清理文本（`char_bigram_baseline` vs `char_bigram_clean`），
  清理后依然喂给同一个未改动的 `char_bigram_tokenizer`。
- **一致/变化的变量**：不清理数字处理，不改 query/标签，不调 BM25 参数，不换知识切分方式——
  只清理标点和空白。
- **运行目录**：项目根目录。本实验不需要 Dense/Chroma，确认知识文本与官方库一致后，在无网络沙箱里
  直接真实执行（不是机制自检占位）。
- **真实/静态/机制自检**：真实运行。
- **结论依据**：真实数据支持。原始样本 Recall@5 从 0.9468 升到 0.9521，但逐场景核对后发现**改善只来自
  一个场景（延迟支付场景）的一次排名变化**（第二十六条从第6名升到第5名，刚好跨过 K=5 的截断线），
  其余 46 个场景完全不变，0 个独占命中。**决策：改善是噪声级别，不是系统性的，不采用 `char_bigram_clean`**，
  保留 `char_bigram_baseline`。

### 07 `eval_bm25_boundary_experiment.py`

- **解决什么问题**：`char_bigram` 过滤空白后直接拼接剩余字符，会把原文中被换行/空格分隔的字符配对
  成从未真实连续出现过的伪 token（例如"工作地点\n乙方"→"点乙"）。按空白边界分段后段内配对，
  能否消除这个伪 token 并提升效果。
- **为什么做**：这是一个真实存在的分词实现问题（不是假设），值得单独验证它是否影响了检索质量。
- **输入**：同 05/06。
- **输出**：`data/eval_samples/results/bm25_boundary_experiment_<时间戳>.json/.md`。
- **关键参数**：同上，唯一变量是是否允许字符二元组跨越空白边界（`char_bigram_baseline` vs
  `char_bigram_boundary_aware`）；分段后片段 <2 字符时产出 0 个 token（不引入 unigram 兜底，
  避免变成"增加了一种新 token 类型"）。
- **一致/变化的变量**：不清理标点、不改数字处理、不改 query/标签、不调 BM25 参数、不换知识切分方式。
- **运行目录**：项目根目录。同 06，无需 Dense/Chroma，直接真实执行。本次运行时沙箱没有安装
  `chromadb`，脚本内复用的官方知识库一致性核验函数**没能跑通**（`ModuleNotFoundError`），
  已在结果文件里如实记录为 `checked: False`，不是假装核验通过；但 `data/knowledge/*.txt` 本轮
  未被修改，和此前几轮（已在用户本机通过真实核验）是同一批文件。
- **真实/静态/机制自检**：真实运行。额外做了分词器正确性的独立验证：确认"点乙"这类跨边界伪
  token 被消除、段内二元组（如"工作/作地/地点"）被正确保留、<2字符片段产出 0 个 token（不是
  unigram 兜底）。
- **结论依据**：真实数据支持。两组指标**完全一致**（两种口径、三个 K 值，数字逐位相同）；
  底层核对发现 26 个知识文档和全部 47 个场景的 BM25 原始分数确实都发生了变化（说明分词器确实
  生效了），但没有任何一个场景的相关法条排名因此改变。**决策：不采用 `char_bigram_boundary_aware`**，
  保留 `char_bigram_baseline`——跨边界伪 token 问题真实存在，但在当前数据集上没有造成可测量的
  检索质量损失。

### 08 `eval_full_sample_diagnostics.py`

- **解决什么问题**：01-07 轮实验只覆盖 188 条有标签样本，另外 127 条没有被检索诊断覆盖过，无法知道
  它们的检索结果长什么样，也无法判断是否有被遗漏的规则候选模式。
- **为什么做**：补全诊断覆盖面，同时为规则候选清单提供更广的样本来源（本轮因此新发现了两个此前
  47 场景分析没覆盖到的重复漏检模式，见第四节）。
- **输入**：`retrieval_eval_samples.json` 的**全部 315 条**（不做 evaluable 过滤）+ 保留版
  `char_bigram` BM25 索引（复用 04/05 的索引构建和分词器，未重新实现）。
- **输出**：`data/eval_samples/full_sample_diagnostics.json/.md`。
- **关键参数**：`candidate_k=20`；`production_top_k=5`（对应 `config/settings.py` 的
  `RETRIEVAL_TOP_K`）。
- **一致/变化的变量**：N/A（诊断脚本，不是策略对照实验；只用一种已保留的策略）。
- **运行目录**：项目根目录。不需要 Dense/Chroma，直接真实执行。
- **真实/静态/机制自检**：真实运行（纯 BM25，无模型依赖）。
- **结论依据**：真实数据支持，见第四节。

### 09 `eval_weighted_rrf_experiment.py`

- **解决什么问题**：04 号实验已经证明对称（1:1）RRF 融合的排序质量不如纯 BM25。本轮验证
  调整 Dense/BM25 在 RRF 公式里的权重比例，能否在保留召回能力的同时改善排序。
- **为什么做**：排除"是不是只是权重配错了"这个可能性，而不是直接放弃 RRF 这条路线。
- **输入**：**直接复用** `retrieval_strategy_experiment_20261011_030953.json`（04 号实验最终真实
  结果）里每个场景已经保存好的 Dense/BM25 `candidate_k=20` 真实候选列表，**没有重新调用
  BGE-M3、没有重新连接 Chroma、没有重新跑 BM25**——这是一轮纯排名融合运算。脚本运行前会先校验
  输入文件里每个场景是否都有完整的 `candidate_k=20` 候选和知识内容指纹，不满足就直接报错退出。
- **输出**：`data/eval_samples/results/weighted_rrf_experiment_<时间戳>.json/.md`。
- **关键参数**：`candidate_k=20`（沿用，不重新检索）；`final_top_k∈{5,10,20}`；`rrf_k=60`
  （沿用 04 号实验，不做参数搜索）；`(dense_weight, bm25_weight)` 四组：`(1,1)`对称基线、
  `(2,1)`Dense偏重、`(1,2)`BM25偏重、`(1,3)`BM25强偏重。
- **一致/变化的变量**：query、标准标签、知识内容、候选列表、`rrf_k`、`candidate_k`、评分公式
  全部固定不变；唯一改变的变量是 `dense_weight`/`bm25_weight` 比例。
- **运行目录**：项目根目录，不需要 Dense/Chroma/BM25 的任何真实调用。
- **真实/静态/机制自检**：**真实运算**（对真实候选列表做真实的加权 RRF 融合和真实评分，只是
  不重新产生候选），脚本内置自检：权重设为 1:1 时重新算出的融合结果与 04 号实验已有的对称
  RRF 结果逐场景（47个）完全一致，验证本脚本的融合实现和已验证过的 `_rrf_fuse()` 等价。
- **结论依据**：真实数据支持。独立场景口径（47个）：

  | 权重方案 | K=5 Recall | K=5 MRR | K=5 nDCG |
  |---|---:|---:|---:|
  | 对称 1:1（基线） | 0.9610 | 0.7571 | 0.8049 |
  | Dense偏重 2:1 | 0.9557 | 0.8050 | 0.8310 |
  | BM25偏重 1:2 | 0.9397 | **0.8766** | **0.8931** |
  | BM25强偏重 1:3 | 0.9291 | 0.8723 | 0.8881 |

  **决策：BM25 偏重 1:2 是四组里排序质量最好的加权方案**（MRR/nDCG 比对称基线明显提升，
  比纯 BM25 单独使用仍有差距：纯 BM25 独立场景 K=5 为 Recall=0.9344/MRR=0.9007/nDCG=0.9020），
  但 Recall@5 比对称基线下降了约 2 个百分点，且继续加大权重到 1:3 并不能再改善排序
  （MRR/nDCG 反而略降），说明权重调整的收益在 1:2 附近已经接近上限，不是"权重越偏向 BM25
  越好"。三项特别检查结果：①四组权重都没有找回 Dense 和 BM25 两个通道都未命中的法条（0处，
  符合 RRF 的数学性质）；②权重偏重方案都会让至少 1 个此前在对称基线 Top-5 内的正确依据掉出
  Top-5（2:1 掉了"合同解除"场景的第四十七条，1:2/1:3 都掉了"加班费"场景的第三十条，1:3 还
  额外掉了"工作地点"场景的第三十五条）；③重点样本里"延迟支付"场景的第二十六条（纯 BM25 排名
  第6，刚好卡在 top_k=5 外一位）在任何权重的 RRF 融合下排名都严重恶化（对称基线18名，BM25强
  偏重也只能拉到17名），说明只要 Dense 完全没找到这个候选，RRF 融合就会把它排得比纯 BM25 单独
  使用时差得多——加权幅度在本轮测试范围内不足以抵消这个效应。**本次只完成实验记录真实结果，
  是否采用加权 RRF（以及采用哪个权重）留给用户确认，未接入生产检索逻辑。**

## 四、315 条样本全量诊断（08 号实验，2026-10-11 真实运行；2026-10-11 第二次修订补充精确命中字段）

`scripts/eval_full_sample_diagnostics.py` 用保留版 `char_bigram` BM25 对全部 315 条样本分别取
Top-5（对应生产 `RETRIEVAL_TOP_K=5`）和 Top-20（对应 `candidate_k=20`）候选，结果：

| 状态 | 数量 | 含义 |
|---|---:|---|
| `verified_hit_top5` | 173 | **Top-5 内命中了该样本全部标准相关法条**（多标签样本要求全部命中，不是至少命中一条） |
| `verified_hit_top20_only` | 12 | Top-5 未能命中全部标准相关法条（可能是零命中，也可能是部分命中——这个状态本身不区分这两种情况），但 Top-20 内能够全部找全 |
| `verified_miss` | 3 | candidate_k=20 内也没有找到任何标准相关法条 |
| `no_gold_label_needs_review` | 127 | 没有标准答案可比对，**不代表检索错误**，不参与任何命中/漏检判定，需要人工核验后才能转入可计算指标的样本集 |

> **本次修订澄清的两个容易误读的地方（原文档表述不够精确，已修正）**：
> 1. `verified_hit_top5` 是"全部标准相关法条都命中"的严格判定，不是"至少命中一条"。
> 2. `verified_hit_top20_only` **不严格等于**"Top-5 零命中、Top-20 才找到"——实测 12 条里只有
>    4 条是 Top-5 真正零命中，另外 8 条其实在 Top-5 内已经命中了部分标准法条，只是没有命中全部。

### Top-5 命中情况三态分布（互斥、覆盖全部 188 条有标签样本）

这组统计直接从「Top-5 实际检索结果」与「标准相关法条集合」的交集数量计算，不从上面的状态名称
反推，是和状态分布互补的另一个角度：

| 分类 | 定义 | 数量 |
|---|---|---:|
| `zero_hit`（零命中） | Top-5 内一条标准相关法条都没找到 | 7 |
| `partial_hit`（部分命中） | Top-5 内命中了至少一条，但没有找全 | 8 |
| `all_hit`（全部命中） | Top-5 内找全了该样本的全部标准相关法条 | 173 |

`all_hit`（173）与状态分布里的 `verified_hit_top5`（173）严格相等，脚本内置断言保证两套算法
（直接计数交集 vs `_score()` 的 recall==1.0）永远一致，不一致会直接报错。`zero_hit + partial_hit`
= 7 + 8 = 15，对应 `verified_hit_top20_only`(12) + `verified_miss`(3) = 15 这组样本集合（总数相等，
但不是逐一对应，因为后者的区分依据是 Top-20 能不能找全，不是 Top-5 命中了几条）。Top-20 口径下
三态分布为 `zero_hit=0、partial_hit=3、all_hit=185`——也就是说 3 条 `verified_miss` 样本在
Top-20 内其实都命中了部分标准法条（多标签样本缺一条没找到），没有一条是 Top-20 内完全零命中。

### Recall@5 宏平均 ≠ `verified_hit_top5` 计数占比

- **Recall@5 宏平均**（逐样本 `命中数/标准相关法条总数` 取平均，和 01-07 轮实验的 Recall@K 公式
  完全一致）= **0.9468**，与表 B/C 里 BM25 char_bigram 188 条口径的历史真实 Recall@5 数字完全一致。
- `verified_hit_top5` 计数占比 = 173/188 = **0.9202**，是"是否全部命中"的二值计数占比，
  **不等于**上面的宏平均 Recall@5。
- 差值（0.9468 − 0.9202 ≈ 0.0266）正好等于全部 `partial_hit` 样本贡献的部分召回分数之和除以 188
  （8 条部分命中样本的 `recall_top5` 分别是 0.5×3、0.667×3、0.75×2，加总后除以188正好补齐这个差值）。
  这不是计算错误，是两个定义不同但都正确的统计量，**不能互相替代或换算**。

188 条有标签样本（`verified_hit_top5` + `verified_hit_top20_only` + `verified_miss` = 188）与
127 条无标签样本在这份诊断里是完全分开统计的两类：前者继续用于计算 Recall/MRR/nDCG 等核心指标
（沿用 01-07 轮的公式，本次没有重算，已有的 A/B/C 节数字继续有效）；后者只记录检索结果本身，
供人工抽查，不参与任何核心指标计算，也不会被标记为"漏检"（127 条的全部命中字段均为 `null`）。

## 五、重要工程问题记录（问题-原因-解决方法-验证结果-限制-决策）

### 问题1：`_evidence_id()` 哈希输入曾增加 `part` 字段，导致旧/新 ID 不一致

- **问题**：对比官方 Chroma 知识库和本次重新切分的知识文本时，按 `_evidence_id()` 哈希比较，得到
  "26 个官方片段、26 个本次片段，数量相等但 id 完全不重叠"的结果，看起来像知识库内容被破坏。
- **原因**：`rag/knowledge_loader.py::_evidence_id()` 在更早的一轮会话里把 `part` 字段加入了哈希
  输入（从3段哈希变成4段哈希），但官方 `data/chroma` 是用旧版哈希写入的，同样的内容算出不同的 id。
- **解决方法**：把一致性核验的**主要判据**从 id 比较改为内容元组 `(source, article, content)` 的
  多重集合比较（`content_match_exactly`），id 比较降级为诊断信息（`ids_match_exactly` +
  `id_mismatch_likely_due_to_hash_scheme_change` 标记）。
- **验证结果**：用构造的 mock chromadb 测试先验证了这个机制的合理性，随后用真实数据确认：
  内容完全一致（`content_match_exactly: true`），id 确实因为哈希算法版本不同而不同。
- **限制**：这个诊断只对比内容和部分元数据，不保证官方库写入时间之后的所有操作都被追踪到。
- **决策**：保留修复后的内容比较逻辑作为知识库一致性核验的主要判据，id 比较仅供参考。

### 问题2：不能仅凭 ID 不一致认定知识内容发生变化，应优先比较实际文本和元数据

（与问题1同一事实的决策总结，单独列出是因为这是贯穿后续所有实验的一条原则）：任何知识库一致性
判断都必须先看内容元组比较结果，id 不一致不能单独作为"内容变了"的证据。

### 问题3：旧 Dense 结果缺少知识片段指纹，强制改为真实重跑

- **问题**：复用旧 Dense Top-K 实验结果时，只核对了样本数/场景数/query/标签/模型名是否一致，
  没有核对旧 Dense 实验**实际索引的知识片段内容**是否和本次 BM25 用的知识片段完全一致。
- **原因**：旧的 `retrieval_topk_experiment_*.json` 只保存了知识片段数量，没有保存内容本身，
  无法事后核验。
- **解决方法**：新增 `_knowledge_content_fingerprint()`（对每条 Evidence 的
  `source\x00article\x00content` 排序后算 sha256），复用条件里加入"指纹必须存在且匹配"这一条
  硬性要求；旧结果文件没有这个字段，所以必然触发真实重跑，且重跑时让 Dense 和 BM25 共用同一份
  Evidence 对象（`loader.index(knowledge_evidences)`），而不是各自独立重新切分。
- **验证结果**：沙箱里用 FakeEmbeddings 验证过"旧结果缺指纹 → 触发 rerun"这条路径能正确走通；
  用户真实机器上的重跑结果与之前"复用"路径算出的数字完全一致（间接证明了之前复用判断在这个
  具体案例里结果是对的，但验证方式本身是不严谨的，所以仍然要改）。
- **限制**：这次重跑只验证了这一份知识快照；如果未来知识库文件再变化，仍然需要重新核验指纹。
- **决策**：以后任何"复用旧结果"的判断都必须有内容级指纹支持，不能只看样本/场景/模型名是否一致。

### 问题4：评估样本存在大量重复条款，需要同时采用两种统计口径

- **问题**：188 条样本中有大量条款模板在不同合同里重复出现（同一个 query + 同一个标准答案出现
  好几次），如果直接对 188 条做 macro 平均，重复出现多的模式会被不成比例地放大。
- **原因**：评估样本是从 50 份合同生成的，合同之间大量复用相同的条款模板（这是样本构造方式决定的，
  不是 bug）。
- **解决方法**：同时维护"原始样本口径"（188条，按真实出现频率加权）和"独立场景口径"（47个
  `(query,标签)` 场景，每个场景等权重），所有实验的所有报告都同时给出两种口径，不合并成一个数字。
- **验证结果**：两种口径在 01-07 轮实验里数字经常不同（例如 BM25 K=5 场景口径 Recall=0.9344，
  样本口径 Recall=0.9468），说明口径选择确实会影响解读，分开报告是必要的。
- **限制**：场景口径对"罕见但重要"的条款类型给了更高权重，样本口径对"常见"的条款类型给了更高
  权重——两者哪个更接近真实使用场景，取决于未来真实合同里各类条款的实际出现频率分布，目前没有
  这个分布的真实数据。
- **决策**：继续同时报告两种口径，不选择其中一种作为"唯一正确"的口径。

### 问题5：`char_bigram` 会产生跨空白边界的伪 token，但当前数据上未观察到可测量的排序变化

- **问题**：`char_bigram` 分词器过滤空白后直接拼接剩余字符，产生类似"点乙"这样原文中不连续出现的
  伪 token。
- **原因**：实现上先 `[c for c in text if not c.isspace()]` 再两两配对，没有把空白当作硬边界。
- **解决方法**：07 号实验实现了 `char_bigram_boundary_aware`（按连续空白分段，段内配对，不跨段），
  单独做控制变量对比。
- **验证结果**：真实运行确认：26/26 篇知识文档和全部 47 个场景的 BM25 原始分数都因为这个改动发生
  变化（说明伪 token 确实存在且被消除了），但没有任何一个场景的相关法条排名因此改变，两种口径、
  三个 K 值的指标完全一致。
- **限制**：这个结论只覆盖当前 188 样本/47 场景这批数据，样本规模有限；不能排除在其他分布（例如
  扫描件噪声更多、query 本身包含更多跨行内容）下跨边界伪 token 会产生实际影响。
- **决策**：问题真实存在，但在当前数据集上没有造成可测量的检索质量损失，不采用
  `char_bigram_boundary_aware`，保留 `char_bigram_baseline`。

### 问题6：RRF 不能召回两个通道均未找到的相关法条，只能对已有候选重新排序

- **问题**：对称 RRF 融合在 04 号实验里提高了部分场景的 Recall，但整体排序质量（MRR/nDCG）比纯
  BM25 差，需要搞清楚它的融合机制到底带来了什么、没带来什么。
- **原因**：RRF 的融合范围是 `dense_candidates ∪ bm25_candidates`，不会凭空产生新的候选文档。
- **解决方法**：对 04 号实验结果做了逐场景分析（47个场景全部检查），确认 RRF 结果集是 Dense 候选集
  和 BM25 候选集的并集子集这一性质是否严格成立。
- **验证结果**：47/47 个场景验证通过，RRF 从未召回过 Dense 和 BM25 两个通道都没找到的法条；同时
  发现 RRF 会拉低一些"只被一个通道找到"的法条的排名（相比该通道单独使用时的排名）。
- **限制**：这个性质在数学上是 RRF 算法本身决定的（必然成立），这里的验证是确认当前实现没有违反
  这个性质，不是发现了新规律。
- **决策**：RRF 定位是"候选排序融合"，不是"召回增强"；当前数据上它没有带来排序质量提升，暂不采用。

## 七、未来所有实验的统一规范

见任务要求原文，摘要如下，新脚本必须遵循：

1. 清晰的脚本名称与编号（延续 `eval_*_experiment.py` 命名，编号写在本文档第二节表格里，不要求
   改文件名）。
2. 脚本开头说明实验目的、控制变量、Top-K、候选深度和运行方式（参考 05-08 号脚本的头部注释格式）。
3. 使用固定评估样本（`retrieval_eval_samples.json`）与明确的知识快照（记录指纹或至少记录片段数量
   和来源）。
4. 保存带时间戳的 JSON 和 Markdown 结果，不覆盖旧结果。
5. 将真实结果与结论同步写入本文档（新增一节，不要只写"实验成功"）。
6. 对全部 315 条样本的适用性：如果新实验只关心有标签的 188 条，可以不跑全量；如果要扩展诊断覆盖面，
   复用 `eval_full_sample_diagnostics.py` 里的 `_load_all_samples()`。
7. 对 188 条有标准标签的数据继续用本文档第一节的评分公式计算核心指标。
8. 对重复、难检索的风险模式，核实后补充进 `rule_candidate_cases.json`（出现 >2 次且不同合同才建议
   提交评审）。
9. 明确哪些结果是真实运行，哪些只是静态检查或模拟机制自检，不得混淆。
10. 不覆盖旧结果；不将实验策略自动接入生产（`rag/retriever.py` 等正式代码路径的修改需要用户单独
    确认）。

后续加权 RRF 实验（尚未开始，入口待建）必须额外记录：每组融合权重、RRF 参数（`rrf_k`）、候选深度
（`candidate_k`）和最终截断深度（`final_top_k`），并像 04 号实验一样在不同策略间强制共享同一份
知识内容指纹，不能用样本数/模型名一致就假定内容一致。
