# RAG 快照指纹机制（任务 C）

状态：**已完成代码编写并通过真实自测**；尚未在用户机器上对接真实 `data/chroma`/真实依赖版本做端到端验证（见第4节限制）。

## 1. 做了什么

新增 `scripts/build_snapshot_fingerprint.py`：对知识库内容、评估数据标准答案、关键配置、
运行环境，各自生成一个"只依赖内容本身、不依赖目录名/文件数量/生成时间"的稳定指纹，并提供
`diff_snapshots()` 用于定位两次快照之间具体哪个文件/哪条 Evidence 发生了变化。

**为什么需要这个**：第一阶段审计已经发现一个真实反例——两次独立切分出的 26 个 chunk 内容
逐字相同，但旧版本 `_evidence_id()` 算出的哈希 id 全部不同（哈希算法版本变了，不是内容变了）。
纯粹"数一数有多少个文件/多少个 chunk"不能证明两次实验用的是同一份知识库内容，必须对内容本身
取指纹。

## 2. 指纹怎么算（设计要点）

- **知识库指纹**：按"第X条"切分（复用 `rag/knowledge_loader.py::_ARTICLE_RE` 完全相同的
  正则），每条取 `(source, article, part, content)` 的 sha256，所有条目的哈希排序后再整体
  取一次哈希——顺序无关、内容敏感。文件级也先取每个文件字节哈希，再排序整体取哈希。
- **评估数据指纹**：只对 `sample_id`、`query`、`evaluable`、`relevant`（标准答案结构化部分）
  这几个真正影响指标计算的字段取哈希，**显式排除** `generated_at` 等纯元数据字段——所以
  "只改生成时间、内容不变"不会导致指纹变化（下面测试 5 验证了这一点）。
- **配置指纹**：`RETRIEVAL_TOP_K`/`EMBEDDING_MODEL_NAME`/`KNOWLEDGE_CHUNK_SIZE` 等。
- **环境指纹**：Python 版本 + 关键依赖（`langchain-chroma`/`chromadb`/`jieba` 等）版本，
  当前沙箱环境没装这些包，字段会如实标注"未安装/无法确认"，不是留空或编造版本号。
- **整体指纹** = `sha256(知识库指纹 + 评估数据指纹 + 配置哈希)`，环境信息记录但不纳入整体
  指纹计算（环境变化不代表数据内容变了，但会单独记录供排查用）。

## 3. 真实自测结果（6 项全部通过，不是声称通过）

本次把脚本和真实拉取下来的项目文件副本放进沙箱，做了真实的增/删/改操作后重新跑指纹函数
（不是 mock，每一项都能看到真实前后指纹值的变化或不变）：

| # | 测试场景 | 结果 |
|---|---|---|
| 1 | 相同输入重复生成两次 | **指纹完全一致**（`5ea17f26...` = `5ea17f26...`） |
| 2 | 在 `劳动合同法.txt` 末尾追加一段文字 | **指纹变化**，且 `diff_snapshots()` 正确定位到是 `劳动合同法.txt` 这个文件变了，具体是 `第八十七条`（最后一条）这条 Evidence 的内容哈希变了（因为追加的文字落在最后一条条文的区间内）——这正是"能查明哪条 Evidence 变了"这项要求 |
| 3 | 删除 `劳动合同法.txt` | **指纹变化**，`diff_snapshots()` 报告 `removed_files: ["劳动合同法.txt"]` |
| 4 | 修改一条标准答案（把某条 `relevant.article` 改成一个不存在的测试值） | **评估数据指纹变化**，同时**知识库指纹保持不变**——证明两个指纹互相独立，改标准答案不会误报知识库变了，反之也一样 |
| 5 | 两次生成快照之间只间隔 1.2 秒（`generated_at` 必然不同），内容不改 | `generated_at` 确认不同，但**整体内容指纹完全一致**——证明生成时间不参与内容指纹计算 |
| 6 | `diff_snapshots()` 能否指出具体哪条 Evidence/哪个文件变了 | 能，见测试 2/3 的结果，不是只给一个"变了/没变"的布尔值 |

## 4. 已知限制（如实说明）

1. **二次切分分支未实现，只是确认当前知识库没有触发它**：真正的 `KnowledgeLoader` 在单条
   法条超过 500 字时会调用 `RecursiveCharacterTextSplitter` 做二次切分。本工具所在的沙箱
   环境没有网络、无法安装 `langchain_text_splitters`，所以没有复用真实的二次切分逻辑，而是
   复用了"按『第X条』一级切分"这个正则本身（和生产代码逐字相同），并实测确认当前知识库全部
   26 条法条最长 289 字，远低于 500 字阈值——**这个简化目前不影响结果的正确性，但如果以后
   知识库里出现超过 500 字的条文，工具会显式报错而不是悄悄给出错误结果**，需要在能装
   `langchain_text_splitters` 的环境里补完这部分。
2. **没有对接真实 `data/chroma`**：本工具测的是"从 `data/knowledge/*.txt` 重新切分出来的
   内容"，不是直接读取 Chroma 里已经写入的向量库内容。两者在本次 Phase 1 审计里已经确认
   content_match_exactly（真实查询 chroma.sqlite3 得到），但这是两条独立的核验路径，不是
   同一个指纹来源，以后如果要做"Chroma 实际内容指纹"，需要另外读 `embeddings`/
   `embedding_metadata` 表。
3. **环境依赖版本采集在当前沙箱里基本是"未安装"**：这反映的是沙箱环境缺依赖，不代表用户
   真实机器上也没装；需要在用户机器上跑一次本脚本才能拿到真实的依赖版本记录。
4. **BM25 的 k1/b 参数是从文档里抄的硬编码值，不是从脚本模块直接读取**：如果后续
   `eval_bm25_tokenizer_experiment.py` 改了这两个常量而文档没同步更新，这里会记录错误的值，
   属于一个已知但优先级不高的简化。
