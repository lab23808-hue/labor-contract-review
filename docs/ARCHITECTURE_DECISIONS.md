## AD-01 为什么使用 LangGraph

- **决策**：Review 主链路用 LangGraph（`StateGraph`）编排，而不是普通函数调用 + 线程池。
- **当时的问题**：LLM Review 和 Rule Check 是两个互不依赖、可以并行跑的分支，需要一种方式表达"并行 + 汇合 + 共享状态"。
- **考虑过的方案**：① 普通函数 + `concurrent.futures.ThreadPoolExecutor` 手写 fork/join；② LangGraph `StateGraph`。
- **为什么选择当前方案**：拓扑用声明式方式写出来，结构可读、可单独测试（graph 测试断言"两个分支都被调用""汇合不覆盖""异常向上抛出"，而不只是测试最终结果）；State 显式类型化；为将来条件边、重试、checkpoint 留出扩展位。
- **没有选择其他方案的原因**：手写线程池能实现同样的并行效果，但拓扑信息散落在代码逻辑里，不容易单独测试"边接对了没有"（如实说明这条判断是按断言逻辑做的推断，没有真的删边验证过）。
- **当前是否仍然成立**：⚠️ 部分成立——当前只用到很小一部分 LangGraph 能力（一个 fork/join），这一点在项目文档里被反复诚实地承认（`docs/DEVLOG.md`/`docs/INTERVIEW.md`）。
- **未来什么时候需要重新评估**：如果 Review 链路后续需要条件边（例如"某类条款额外走一轮检索"）或需要 checkpoint/重试，LangGraph 的价值会明显超过手写线程池；如果链路复杂度一直不增加，需要诚实评估"是否值得继续维护这个依赖"。

## AD-02 为什么 Review 是 Graph（State/Node/Edge 具体设计）

- **决策**：State 只放 6 个字段，每字段单一写入者；Node 是"薄封装"，业务逻辑留在可独立测试的模块里；Edge 全部是无条件边。
- **当时的问题**：需要决定"哪些数据要经过 State 传递""失败了怎么办"。
- **考虑过的方案**：① 把 `Evidence`/`ReviewReport`/基础设施实例也塞进 State；② 加一个 `error` 字段配合条件边做失败路由。
- **为什么选择当前方案**：判断标准是"下一个节点是否把它当直接输入"——`Evidence` 没有下游节点用、`ReviewReport` 明确决定不进（调用方用最终 State 重建）；每字段单一写入者就不需要 reducer，State 保持简单可读。
- **没有选择其他方案的原因**：加 `error` 字段和条件边需要先想清楚"节点级失败"的完整语义（谁负责重试、重试几次、失败后整图怎么办），而当时没有真实数据支撑这个设计，先跑通主链路更重要。
- **当前是否仍然成立**：✅ 仍然成立，Phase 3（V2 复审）直接复用同一套 State 设计，没有出现需要扩大 State 的真实场景。
- **未来什么时候需要重新评估**：如果"解析失败导致整次审查崩溃"在真实使用中变得常见（用户反复反馈这个问题），需要重新评估是否加错误路由。

## AD-03 为什么 RAG 是证据层

- **决策**：RAG 只负责"给条款找法律依据"，不参与"决定审查哪些条款"或"决定风险判断"。
- **当时的问题**：如果让检索结果直接决定风险判断（"检索到相关法条就一定有问题"），会绕过 LLM 的语义判断能力，退化成关键词匹配。
- **考虑过的方案**：① RAG 直接产出风险结论；② RAG 只做证据检索，风险判断交给 LLM。
- **为什么选择当前方案**：法律判断需要理解上下文（例如"试用期工资是否合规"取决于具体比例和期限组合），纯检索无法做到；让 LLM 基于检索到的真实依据判断，能兼顾"不编造"和"能理解语义"。
- **没有选择其他方案的原因**：直接用检索结果做判断会让系统退化成关键词命中规则，准确率和可解释性都会下降。
- **当前是否仍然成立**：✅ 仍然成立。
- **未来什么时候需要重新评估**：如果知识库规模扩大到需要多轮检索/重排序，可能需要在 RAG 层增加更复杂的检索策略，但"RAG 只提供证据、不做判断"这条边界本身不需要变。

## AD-04 为什么 RuleChecker 是补充，而不是替代或前置

- **决策**：RuleChecker 独立于 LLM 运行（不读 `llm_results`），结果与 LLM 结果纯拼接。
- **当时的问题**：真实数据发现 LLM 单条款审查有结构性盲区（看不到其他条款）和非确定性（P-04/P-05），需要一种确定性的补充手段。
- **考虑过的方案**：① 统一事实抽取层 `ContractFacts` + 通用规则引擎（第一版做过，见 P-06）；② 规则只在 LLM"不确定"时运行；③ 规则独立运行，结果拼接。
- **为什么选择当前方案**：真实使用方式证明规则应该是"逐条沉淀的测试驱动补丁"，不是通用引擎——先做通用抽象是过度设计；"只在 LLM 不确定时运行"会让规则的价值受制于 LLM 的自我评估，不可靠。
- **没有选择其他方案的原因**：`ContractFacts` 写完后发现和真实使用方式（哪类问题被漏检就补哪条规则）不匹配，删除是及时止损；"依赖 LLM 判断触发"违反了"规则必须能独立测试"的要求。
- **当前是否仍然成立**：✅ 仍然成立，2 条规则均按这个模式实现。
- **未来什么时候需要重新评估**：如果规则数量增长到需要共享提取逻辑（当前约定的触发线是"出现第二条需要同一段提取逻辑的规则"），再抽成共享小函数，仍不恢复 `ContractFacts`。

## AD-05 为什么所有条款仍然需要 LLM Review（不能只靠规则）

- **决策**：即使 RuleChecker 存在，每个条款仍然要经过完整的 LLM Review，不是"规则覆盖到的条款跳过 LLM"。
- **当时的问题**：规则只覆盖 2 类问题（试用期工资、试用期期限），绝大部分条款类型（竞业限制、保密、解除条件等）没有对应规则。
- **考虑过的方案**：① 只对规则未覆盖的条款跑 LLM；② 所有条款都跑 LLM，规则作为补充叠加。
- **为什么选择当前方案**：规则覆盖面太窄，"只对未覆盖条款跑 LLM"意味着大部分风险判断能力完全依赖后续不断新增规则，短期内系统能力会严重不足；LLM Review 全覆盖 + 规则补充确定性/跨条款能力，是当前阶段能落地的最优组合。
- **没有选择其他方案的原因**：规则的开发成本远高于让 LLM 普遍覆盖，且规则测试驱动的开发方式决定了它必然是"慢慢补"的过程。
- **当前是否仍然成立**：✅ 仍然成立。
- **未来什么时候需要重新评估**：如果规则数量和覆盖面显著扩大（例如覆盖到 10+ 类高频问题），可以重新评估"规则覆盖到的条款是否还需要 LLM 重复判断"，但目前证据不足以支持这个优化。

## AD-06 为什么暂时不做强 Tool Selection Agent

- **决策**：Modification Agent 第一版只有一个工具（`modify_clause`），不做多工具自主选择。
- **当时的问题**：设计 Modification Agent 时需要决定"工具集要设计成可扩展的多工具框架，还是先做单工具"。
- **考虑过的方案**：① 一开始就设计通用的多工具选择框架；② 先做单工具，验证核心链路（Function Calling→Validator→HITL）跑通。
- **为什么选择当前方案**：当前业务需求只有"修改单个条款"这一种操作，"选哪个工具"这个问题根本不存在；过早设计多工具框架是没有真实需求支撑的过度设计（与 `rules/` 模块 `ContractFacts` 的教训一致，见 P-06）。
- **没有选择其他方案的原因**：多工具框架需要设计"工具之间如何协作/排他/组合"，这些设计决策在只有一个工具的情况下无法被真实验证，容易做错。
- **当前是否仍然成立**：✅ 仍然成立。
- **未来什么时候需要重新评估**：当业务需要"新增条款""删除条款""跨条款联动修改"等多种操作时，在 `modification/agent.py` 与 `modification/service.py` 之间加一层工具选择/路由逻辑，不需要改动 Review 主图。

## AD-07 为什么 Modification Agent 只有一个核心工具

- **决策**：同 AD-06，`modify_clause` 是唯一工具，且职责单一（只生成修改后的文本+理由+依据，不做范围判断——范围判断交给 Validator）。
- **当时的问题**：工具的职责边界如果设计得太宽（例如让工具自己判断"能不能改""改得对不对"），会让 LLM 承担本可以用确定性代码可靠完成的工作。
- **考虑过的方案**：① 工具只负责生成文本，校验完全交给外部 Validator；② 工具内部就做校验，模型自己判断是否越界。
- **为什么选择当前方案**：越界修改、占位符、条款编号丢失这类问题用固定规则就能可靠检测，不需要再调用一次 LLM"自证"；LLM 更擅长"生成"，不擅长"可靠地自我审查"。
- **没有选择其他方案的原因**：让模型自己判断是否越界，仍然可能出现模型"觉得自己没越界"但实际越界的情况，无法提供工程上可信的保证。
- **当前是否仍然成立**：✅ 仍然成立。
- **未来什么时候需要重新评估**：不适用（这是一条关于"职责分离"的通用原则，不依赖具体业务规模）。

## AD-08 为什么必须 Human Confirmation

- **决策**：Modification Agent 生成的候选，无论 Validator 是否通过，都不会自动生效，必须由律师显式调用 `confirm`。
- **当时的问题**：合同修改是高风险操作，如果允许 LLM 生成的文本自动进入 V2，一旦出错（哪怕 Validator 没检测出来的问题）后果是"生成了一份有问题的正式合同"。
- **考虑过的方案**：① Validator 通过就自动确认；② 必须人工确认。
- **为什么选择当前方案**：Validator 只能检测结构性问题（越界/占位符/编号丢失），检测不了"这样改是否真的符合律师的商业意图、是否有法律风险"这类需要专业判断的问题；这类判断只能交给人。
- **没有选择其他方案的原因**：自动确认会把系统从"辅助工具"变成"自主决策系统"，超出了项目的定位（面向愿意做最终判断的专业用户）。
- **当前是否仍然成立**：✅ 仍然成立，且是整个项目最核心的安全边界之一。
- **未来什么时候需要重新评估**：不建议评估——除非未来有法律/合规层面的明确许可，这条边界不应该被放松。

## AD-09 为什么 Reject 从 V1 + 累积意见重新生成

- **决策**：`start_modification` 永远基于 `task.original_text`（V1 原文）和 `task.lawyer_instructions`（全部历史意见）重新调用 Agent，Prompt 构造函数本身不接受"上一轮候选文本"这个参数。
- **当时的问题**：如果基于上一轮候选继续改，一旦某一轮候选引入了结构性问题（例如误删了交叉引用），后续重试可能在这个错误基础上越改越乱。
- **考虑过的方案**：① 基于上一轮候选做增量修改；② 永远基于原文+累积意见重新生成。
- **为什么选择当前方案**：从代码结构上直接排除"在错误结果上继续叠加"的可能性，比"靠 Prompt 提醒模型不要在错误基础上改"更可靠（Prompt 层面的约束可能被模型忽略）。
- **没有选择其他方案的原因**：增量修改在工程上更难保证"每一轮的输入都是干净的"，且没有真实证据表明增量修改在效果上更好。
- **当前是否仍然成立**：✅ 仍然成立。
- **未来什么时候需要重新评估**：如果未来支持"多轮协商式修改"（律师和 Agent 来回讨论细节），可能需要重新设计这套机制；当前证据不支持这个需求存在。

## AD-10 为什么最多 3 次重试、失败后 needs_human

- **决策**：`MAX_MODIFICATION_ATTEMPTS = 3`，用满仍未确认则进入 `needs_human` 终态。
- **当时的问题**：需要在"给模型足够机会改对"和"避免无限重试消耗成本又给不出结果"之间做取舍。
- **考虑过的方案**：① 无限重试直到成功；② 固定次数上限 + 明确失败终态。
- **为什么选择当前方案**：无限重试在工程上没有终止条件，也无法向律师传达"这个任务卡住了，需要人工介入"这个明确信号；固定次数上限提供了可预测的成本边界和明确的状态转移。
- **没有选择其他方案的原因**：无限重试如果模型持续给出不合格候选（例如反复触发 Validator 的同一条规则），会无限消耗 LLM 调用成本却不产出任何进展。
- **当前是否仍然成立**：✅ 仍然成立；3 这个具体数字**未见到基于真实数据调优的记录**（未找到证据表明测试过 2 次或 5 次的效果差异），是一个经验值。
- **未来什么时候需要重新评估**：如果真实使用中发现"3 次经常不够"或"2 次就足够"，应该用真实数据重新评估这个数字。

## AD-11 为什么 V1 不覆盖

- **决策**：V1（原始 `contract_id` 对应的全部数据）在任何情况下都不会被 V2 生成流程修改。
- **当时的问题**：合同审查场景下，原始文件是法律意义上的审计依据，一旦被修改就丧失了"这是律师最初审查的版本"这个事实。
- **考虑过的方案**：① 直接在 V1 的数据上应用修改；② V2 是完全独立的一份新数据。
- **为什么选择当前方案**：`ContractManager` 从 Phase 1/2 就确立了"原始文件只写一次，拒绝覆盖"的硬约束，V2 直接复用这条约束，不为它破例。
- **没有选择其他方案的原因**：直接覆盖 V1 会让"之前审查过的是什么内容"这个问题变得不可追溯。
- **当前是否仍然成立**：✅ 仍然成立，是本项目最基础的数据完整性保证之一。
- **未来什么时候需要重新评估**：不适用。

## AD-12 为什么 V2 必须重新解析、切分、Review

- **决策**：V2 不是"在 V1 的 Clause 列表上打补丁"，而是完整走一遍 `create_contract`→`parse_contract`→`split_contract`→`run_review`。
- **当时的问题**：V2 全文内容和 V1 不同，需要决定"怎么让 V2 拥有自己正确的 Clause 列表和审查结果"。
- **考虑过的方案**：① 手写"局部更新已有 Clause 列表"的逻辑；② 完整重新走一遍已验证过的流程。
- **为什么选择当前方案**：复用完全未改动的函数，不引入新的偏移量计算逻辑，最大程度降低引入新 bug 的风险；"V2 的风险判断必须是完整、独立的一次审查"这一点本身也是业务要求（不能假设"没改的条款风险判断不需要更新"，因为 LLM 的非确定性意味着重新审查可能给出不同结果，这本身也是 Risk Diff 想要捕捉的信息）。
- **没有选择其他方案的原因**："局部更新"需要处理"条款编号是否变化""偏移量是否需要重新计算"等一系列复杂情况，且没有被验证过；完整重新走一遍虽然计算成本更高，但正确性有保证。
- **当前是否仍然成立**：✅ 仍然成立，且真实验证（P-22/23/24）证明了即使是"完整重新走一遍"这个思路本身没错，具体实现细节（V2 全文重建）仍然踩了三个真实坑，说明这条路径本身已经比预想的更复杂，改用"局部更新"只会引入更多风险。
- **未来什么时候需要重新评估**：如果 V2 生成的性能成为真实瓶颈（例如合同很大、审查很慢），可以重新评估是否需要增量式的部分重审。

## AD-13 为什么 ContractManager 当前使用 filesystem-JSON，暂时不用 SQLite

- **决策**：所有持久化数据（合同、条款、审查记录、修改任务、版本映射）都是本地文件系统上的 JSON 文件。
- **当时的问题**：早期需求文档提到过用 SQLite 保存元数据（`schemas/contract.py`/`schemas/_time.py` 的文档字符串至今仍留有这个说法，属于文档漂移，详见 P-16/P-17），但最终实现走了文件系统路线。
- **考虑过的方案**：① SQLite；② 纯文件系统 JSON。
- **为什么选择当前方案**：当前只需要"按合同隔离的中间产物"，没有跨合同查询、没有并发写入、没有事务需求；文件系统实现简单、可以直接用文件浏览器查看调试，且已经用"临时文件+`os.replace`"解决了写入原子性问题。
- **没有选择其他方案的原因**：这个决定**在开发期间没有被正式确认过**（`docs/DEVLOG.md` 3.2 原文明确写"这个差异开发期间没有正式确认过"），是一个在实现过程中自然发生、但未经过显式设计评审的选择。
- **当前是否仍然成立**：⚠️ 部分成立——Phase 3 新增的 `review/`/`modification_tasks/`/`versions/` 三个子目录各自独立编号，没有跨文件事务保护，真实并发场景（例如同时对同一任务调用两次 `start`）未经验证，是潜在风险点。
- **未来什么时候需要重新评估**：如果需要跨合同检索（"找出所有含竞业限制条款的合同"）、需要并发写入保护、需要审计查询（"某个时间段内所有被确认的修改"），应该评估引入 SQLite 或其他数据库。

## AD-14 bridge 模块未来是否需要删除

- **决策**（沿用 Phase 1/2 的记录）：`parser/contract_parser.py::parse_contract`、`clause/contract_clause_splitter.py::split_contract` 是"连接 ContractManager 与 DocumentParser/ClauseSplitter 的过渡桥接"，`docs/DEVLOG.md` 原文多次提到"桥接文件被 pipeline 收编"是待办事项。
- **当时的问题**：Review Pipeline（LangGraph）和 Modification（V2 生成）都需要调用"解析+切分"这个组合动作，当初用两个独立的桥接函数实现。
- **考虑过的方案**：① 保留桥接函数，各处直接调用；② 把桥接逻辑收编进 `review/pipeline.py` 的节点内部或某个更高层的编排模块。
- **为什么选择当前方案（保留桥接）**：**本次整理观察到**，Phase 3 的 `modification/service.py::generate_v2` 同样直接复用了这两个桥接函数（`parse_contract`/`split_contract`），这实际上证明了桥接函数不是"过渡期的临时代码"，而是**两条独立业务链路（Review、Modification）共同需要的复用点**——如果当初"收编进 pipeline"，Modification 就无法复用，还得再写一遍。
- **没有选择其他方案的原因**：不适用（当前方案是观察到的既成事实，本次整理是"发现原计划被自然推翻"，而不是主动做出的新决策）。
- **当前是否仍然成立**：✅ 仍然成立，且本次整理认为"桥接文件被 pipeline 收编"这条待办事项**应该重新评估、甚至可能不再需要执行**——因为收编会破坏 Modification 对同一套逻辑的复用。
- **未来什么时候需要重新评估**：如果未来出现第三条需要"解析+切分"的业务链路，应该趁机把这两个桥接函数提升为一个更正式的、有自己文档的公共入口，而不是继续叫"桥接"。
